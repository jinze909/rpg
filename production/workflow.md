# 工作室开发流程

本流程适配自 [Claude Code Game Studios](https://github.com/Donchitos/Claude-Code-Game-Studios/tree/05ad7c8a5b8aa2aa86bbd3439ae7cf7295cac418) 的角色分层、任务开发、证据验收与接力做法。保留 [MIT 许可](../docs/CLAUDE_CODE_GAME_STUDIOS_LICENSE.txt)。以本仓库的 [18 个角色](team.md) 和 [冻结范围](../BACKLOG.md#冻结范围) 为准。

ChatGPT 从 [对话入口](../CHATGPT.md) 开始，Codex 从 `AGENTS.md` 开始，Claude Code 可用 `/dev-story [story-path]` 和 `/story-done [story-path]`。三个入口共用同一套角色、任务与证据。

## 现代化候选与零费用验收门槛

执行任何现代 Unity 技术迁移前，先读 [现代 2D RPG 工作室技术基线](../docs/technical/MODERN_2D_RPG_STACK.md)。新的用户硬限制覆盖旧的泛升级建议：**ORK 3.22.0 / Makinom 2.21.0 原厂文件、版本、GUID、配置、数据不动；UGUI 留用；新增购买、订阅和云/CI 收费为零**。需要付费或触动冻结框架的方案停下，不自动“修兼容”或申请授权。

迁移必须是有玩家/维护收益的单项增量，不得在一个候选中同时换渲染、输入、摄像机与动画，更不能叠加到有失败的 P2 救援候选。Producer 与 technical-director 先列现状 SHA、成本、兼容版本和回滚路径；lead-programmer 审查 `manifest.json`、锁文件、场景和 `.meta`；qa-lead 逐项验证 Unity 编译、ORK 状态、UGUI、Bootstrap/声井重载、相机截图、键鼠/手柄等被影响路径。只接受同一最终 SHA 的真实结果。纯文档路线图不触发安装或“已升级”状态。

## Prepare · 选任务

1. Producer 确认实时 `codex/dev` HEAD，读取 [AI2-STATUS](../AI2-STATUS.md)、[BACKLOG](../BACKLOG.md) 和相关 CI。
2. 选一个可验收的增量。记录目标、依赖、改动边界和验收办法。涉及体验或范围时用 creative-director，涉及架构、构建或 CI 时用 technical-director。QA lead 在动手前确定要收集的证据。
3. 具备条件时开始实际实现，把任务标为进行中。缺少运行环境时，推进可独立验证的工作并保留阻塞。

## Implement · 实现

1. 按 [角色表](team.md) 选择专家和负责人。优先使用 ORK 数据、Makinom Schematics 和 Unity 2D 原生表现层，并保留序列化引用与 `.meta`。
2. 涉及画面时由 art-director 判断是否标注 `ART_REVIEW_REQUIRED`。性能指标由 performance-analyst 解释趋势，保留采集条件和比较基线。
3. Lead-programmer 在每次提交前审查实际差异。能使用 Git 时运行 `git diff --check` 与 `git diff --cached --check`。通过 GitHub 对话写入时，审查基线和完整变更文件，重新确认远端 HEAD 后快进发布。

## Verify · 证据

| 变更类型 | 所需证据 |
| --- | --- |
| Unity 代码、场景、程序集或项目数据 | 锁定版本的 Unity 导入与编译。运行行为变化时验证受影响的玩家路径。 |
| 战斗、移动、交互、存档 | 相关 EditMode 或 PlayMode 测试，或可复现的运行验证。 |
| HUD、菜单、美术与动画 | Play Mode 观察，附相关状态截图或录屏。涉及输入时验证相应键鼠与手柄路径。 |
| P0-b 冒烟、P2 原型验收 | 记录脚本入口、实际结果、日志或 artifact。性能数据附环境和采集条件。 |
| 流程或文档 | 检查配置格式、引用与实际读写路径，在客户端可用时验证入口。 |

### 同 SHA 验收

- 每条证据记录所测的完整提交 SHA、检查命令或人工复现步骤、结果和可追溯链接。CI 按运行的提交 SHA 关联，只有分支名、PR 状态或旧提交的通过结果不能证明当前候选已通过。
- QA lead 分别标记通过、失败、运行中、受阻或未运行。全部必需证据针对同一个候选 SHA 且通过后，才将该候选的故事标为完成。未验收的实现可保留待验证状态。
- 验证可发生在发布候选之后。允许另提交纯状态记录，明确记录已验证的候选 SHA。状态提交自身不继承该 SHA 的绿色状态。候选实现改动后重新验证。`green/*` 标签只指向对应的已验证 SHA。

## Handoff · 接力

Producer 更新 `AI2-STATUS.md` 和 `BACKLOG.md` 中发生变化的状态，注明测试 SHA、证据、阻塞和一个下一步。用户授权发布时，确认远端分支指向本轮提交，并在回复中附提交与证据。保持 [长期基线](session-state/active.md) 简明。

### 候选分支清理

**用户现已明确取消 M1–M11 阶段分支的永久保留特例。** 本规则覆盖 2026-11-09 的旧保留约定：M1–M11 与其他 `codex/pending/*` 一视同仁。Git Commit、Issues 与 CI/artifact 才是历史证据，分支指针不需要永久保留。

1. **每次候选实际成功并入 `codex/dev`（安全快进或合并）后，立即触发一次分支清理检查**。Producer 查询最新 `codex/dev` HEAD 和**全部** `codex/pending/*`，不限于本次候选，并在开始下一项开发前完成适用清理。**单纯聊天轮次结束、候选提交、CI 排队/运行、失败修复、未合入的交付汇报，不触发全量扫描**；优先修复 CI 失败，避免为了清理阻塞正常开发。
2. 如果分支 HEAD 是 `codex/dev` 的祖先或与其相同，且不存在开放 PR、排队/运行中的 CI、未完成验收、当前接力依赖、其他开发者在用的工作或分支保护，立即列为可删并执行删除。**M1–M11 阶段头完全相同，无永久保留豁免**。
3. 对 rebase、cherry-pick、整合提交后仍有独有历史的分支，不可仅因不同 SHA 无限保留；但也不能仅凭分支名、相似代码或旧绿色 CI 删除。先查独有变更、最终已交付实现、同 SHA CI 和接力记录；**确证已完全交付或明确废弃且没有任何依赖后**才可删。不能证实则保留并说明具体原因。
4. 绝对禁止删除 `main`、`codex/dev`、仓库默认/受保护分支、有开放 PR、CI 正在排队或运行、存在未交付独有工作、未完成验收或仍为他人使用的分支。不得以 force push、清空内容或改写历史代替分支删除。
5. 删除前**再次读取远端完整分支 SHA**、PR、CI、保护与接力依赖，并确认没有移动；删除操作必须以该已核实 SHA 为目标，防止竞争更新。删除后重新查询远端，证明确实消失。发现 HEAD 移动或状态不明则保留并报告。
6. 清理记录须保留分支名、源 HEAD SHA、合入后的最终 SHA、CI run/artifact 链接和实际结果。该操作不需要空提交或无意义文档。
7. 如果当前连接**没有安全删除分支的工具或权限**，不得说已清理，也不得尝试危险替代操作。明确报告已经确认可删但未删除的分支与限制，提供需用户/受权工具执行的安全删除路径，同时继续其他可独立开发工作。
8. **发生实际 `codex/dev` 合入的交付回复**须简报实际删除数量、剩余分支的保留原因与无法执行的清理事项；**未发生合入的轮次不要求全量分支检查或清理报告**。清理是成功合入后的收尾步骤，不应无限延期，也不修改 Muse 或任何调度。
