- Product priority: **fun comes first**. Every story, content, system and production decision must serve an engaging player experience. Scope, word count, feature count and technical completion do not establish that an experience is fun. State what players actually do, discover or care about; validate uncertain assumptions through play and revise or remove elements that weaken the experience. Narrative depth and content scale remain goals on this foundation.

Reconcile old candidate merges against the latest `codex/dev` narrative and never restore superseded drafts. Narrative P0, technical P0 and existing Unity S00 are distinct. This is a writing/design baseline, not implemented gameplay or proof of fun. Preserve the midpoint reunion, substantial shared adventures afterward, and independently worthwhile regional stories.
- Read the [one-page gameplay baseline](docs/gameplay/BASELINE.md) before gameplay work. Preserve its distinction between decided direction, provisional prototype controls and unvalidated hypotheses; task execution must not silently promote the latter two into product requirements.
- Work in `jinze909/rpg`. Resolve the live `codex/dev` HEAD and read [AI2-STATUS](AI2-STATUS.md), [BACKLOG](BACKLOG.md), and [the team roster](production/team.md) at that revision before editing.

## Mandatory subagent-capable studio workflow

**Trigger and authority.** If the executing agent actually has callable subagent/delegation capabilities and may use them under the current permissions and zero-new-cost boundary, it **MUST use real, task-scoped delegation** for substantive development under this repository's adapted [Claude Code Game Studios workflow](production/workflow.md), [18-role roster](production/team.md), and applicable [role definitions](.claude/agents/) and [story skills](.claude/skills/). This applies to ChatGPT, Codex, Claude Code, or any other agent with such capabilities; the tool syntax may differ, but the required responsibilities and acceptance gates do not. Merely writing role names, claiming a simulated team, or treating an unreviewed single-agent result as an independent subagent review does **not** meet the delegation requirement.

1. **Prepare — producer / coordinator.** The main agent remains the accountable producer/coordinator: check the live full `codex/dev` SHA, current active candidates and CI, [AI2-STATUS](AI2-STATUS.md), [BACKLOG](BACKLOG.md), and the relevant story and gameplay/narrative baselines. Define one bounded, independently verifiable increment, its file ownership/dependencies and rollback, player value, and acceptance evidence before delegating. Consult `creative-director` for material story, player-experience, or scope decisions; `technical-director` for architecture, framework, build, or CI risk.
2. **Implement — relevant specialist subagents.** Delegate implementation/research/validation to the *relevant* roles from `production/team.md` and `.claude/agents/` (for example, `gameplay-programmer`, `ui-programmer`, `level-designer`, `technical-artist`, `unity-specialist`, or `qa-tester`). Give each a concrete scope, starting SHA, owned paths, deliverable and evidence requirements. Parallelize only truly independent work; do not allow overlapping edits, competing state authorities, writes to a running candidate's tested SHA, or unreviewed overwrites of another contributor's work. The main agent integrates the actual results rather than treating subagent opinions as code changes.
3. **Review — lead-programmer.** Before each code/asset/workflow submission, have the `lead-programmer` role examine the final actual diff, module and ORK/Makinom/Unity ownership, references/`.meta`, compatibility, failure modes, test coverage, and conflicts with newer `codex/dev`. Use a separate callable reviewer when available and permitted; address concrete findings before publishing. The main agent retains responsibility for safe commits, branch updates, and merges.
4. **Verify — qa-lead.** Have `qa-lead` define the acceptance criteria and evidence plan **before implementation**, then independently compare the finished changes with real reproducible evidence; use `qa-tester` or the appropriate specialist for execution where useful. Delegate this QA review to an actual separate subagent when available and permitted; otherwise perform and document the QA role checks in the main session without pretending independent review. Require the existing final-SHA clean Unity/Actions checks and affected gameplay, input, UI and visual evidence as specified in [Verify](production/workflow.md) and [same-SHA acceptance](production/workflow.md). Distinguish passed, failed, pending, blocked, and unrun; never call prepare success, a simulated playthrough, or an uninspected screenshot a validated deliverable.
5. **Handoff — producer / coordinator.** Record the actual files/commits, candidate full SHA, CI Run/artifacts, review findings, unresolved risks, implementation next step, and agent-verification next step. Merge only an already verified and safe candidate; the main agent makes final repository mutations and reports what actually happened. Maintain the existing independent A/B work tracks when another candidate's CI is queued or running.

**Availability and proportionality.** The producer, lead-programmer and qa-lead role checks are mandatory at their applicable stages. For substantive implementation, if at least one permitted subagent is callable, assign meaningful work to at least one **real** subagent in a relevant specialist/review/QA role; delegate the lead-programmer and qa-lead checks to distinct reviewer contexts where the available capabilities permit, without inventing agents or forcing parallel execution. If only limited delegation is possible, the main agent explicitly performs any remaining role checks and records the limitation; if delegation is genuinely unavailable, disallowed or would incur unapproved cost, perform all role checks sequentially. Never halt safe work or ask the user to assemble the team. Even with subagents, **do not invoke all 18 roles by default, hold routine multi-agent meetings, duplicate reviews for ceremony, or wait for unrelated agents/CI before independent development**. For a narrow instruction/documentation change, apply the relevant review without spawning irrelevant implementation roles.

**Precedence and safety.** This section makes real role delegation compulsory *when usable*; it does not change the project's existing product direction, story canon, single RPG authority, no-new-cost/licensing/credentials rule, `codex/pending/*` lifecycle, same-final-SHA CI gate, or ban on changing Muse/cron/scheduling. Repository-specific `AGENTS.md`, `CHATGPT.md`, `production/workflow.md`, and story acceptance criteria still govern the work; never use delegation as a reason to bypass them.

## Mandatory visual and UI acceptance criteria (2026-11-19)

- **Full-scale, explorable RPG maps:** Never compress primary playable levels or maps into undersized, box-like areas. Every main exploration scene must use a normal RPG map scale with camera following and clearly differentiated spatial zones.
- **Never obstruct the playable world:** UI buttons and panels must not cover playable map areas, walls, or characters.
- **Never show duplicated or overlapping titles:** Do not render titles from two Canvas layers simultaneously. When combat or another subview opens, hide any conflicting underlying titles, dialogue, and entry buttons.
- **Never display a wall of debug text:** Do not place multiline plain-text debug snapshots such as `BuildBattleReadout` in the center of the screen. Present combat information using compact status cards, visual health bars, and a command bar in reserved, non-obstructing UI space.
- **Use readable pixel fonts for body text:** Do not use thick, rounded, poster-style display fonts such as `ZCOOLQingKeHuangYou` for body text or buttons. Use a sharp, legible, open-source pixel font such as Fusion Pixel 12px/10px.
- **Maintain consistent safe-area layout and visuals:** Arrange all new or modified UI in reserved, non-obstructing space with consistent dark backing panels and thin borders. For every visual/UI upgrade, produce and inspect actual GameView screenshots, checking that titles do not overlap, buttons do not cover the map, and glyphs do not run together.

- **Framework changes are authorized after sufficient validation.** ORK/Makinom framework code, DLLs, settings, configuration and game data are not read-only. Make necessary changes in isolated candidates, record baseline/impact/rollback, preserve provenance and references, and pass the affected paths at the final SHA before integration. Follow [framework validation](production/workflow.md); do not ask for routine approval. Keep a single RPG authority, UGUI, existing licensing, and zero new spending. Version changes need the same evidence, not a blanket ban or an automatic upgrade.
- **Autonomous delivery and verification:** do not require the user to playtest, review media, run tools or post GitHub feedback. Agents run available checks and record defects, unknowns and blocked evidence in [known issues](production/KNOWN_ISSUES.md). No human-feedback gate; no claim that automation proves enjoyment. Record both implementation and agent-verification next steps.
- Prioritize merging a ready, verified candidate before unrelated governance changes; allow independent work and urgent changes. Reuse trustworthy evidence only for identical final SHA and equivalent verification conditions. Do not impose a fixed WIP cap or a broad test-refactoring milestone.
- Prefer released, Unity-version-compatible official Unity Registry packages or built-in features, but **plan first; install only in isolated, same-SHA-validated candidates**. Evaluate URP 2D, Input System in **Both** mode, Cinemachine 3, 2D animation, Tilemap Extras, audio mixer, Sprite Atlas V2, conditional Pixel Perfect, localization, profiling and Build Profiles; defer Addressables/ECS/HDRP until their need is demonstrated. No paid services or extra CI spending without new authorization.
- **Non-blocking CI handoff (2026-11-11, mandatory):** A pending/queued/running Unity CI blocks validation/merging of that exact candidate SHA only, **not new independent implementation**. During every dispatched development turn, maintain (A) existing candidate/CI triage (latest SHA; stale failing SHA superseded by a newer queued fix is not an actionable fresh failure) and (B) independent, non-overlapping gameplay/code/test/resource development on another candidate from current dev. If all available candidate CI is queued, proactively select unclaimed valuable work from BACKLOG/stories, make a real change, and commit it to a separate candidate without modifying tested refs. Never end with only 'CI still running' unless every feasible independent task has a specific demonstrated dependency/conflict/permission blocker. Do not fabricate commits, rerun duplicate CI, edit schedules, or create busywork. Details in [workflow](production/workflow.md). Already queued runs require no polling loop. Never overwrite newer guidance when rebasing an old pending branch.
- **Current user decision (2026-11-10): no automatic M1-M11-before-Story-003 priority.** Modernization M1-M11, game stories, gameplay, narrative, and regression fixes are all eligible workstreams. Pick the next independently verifiable increment by real player value, live dependencies, unresolved defects, and the current handoff—not by a mandatory migration sequence or an automatic story preference.
