# RPG development

- Product priority: **fun comes first**. Every story, content, system and production decision must serve an engaging player experience. Scope, word count, feature count and technical completion do not establish that an experience is fun. State what players actually do, discover or care about; validate uncertain assumptions through play and revise or remove elements that weaken the experience. Narrative depth and content scale remain goals on this foundation.
- The current narrative baseline is the [Return story outline](docs/narrative/STORY_OUTLINE.md), with linked character and regional story documents. Treat it as a writing/design baseline, not implemented gameplay or proof of fun. Preserve the midpoint reunion, substantial shared adventures afterward, and independently worthwhile regional stories when extending it.
- Read the [one-page gameplay baseline](docs/gameplay/BASELINE.md) before gameplay work. Preserve its distinction between decided direction, provisional prototype controls and unvalidated hypotheses; task execution must not silently promote the latter two into product requirements.
- Work in `jinze909/rpg`. Resolve the live `codex/dev` HEAD and read [AI2-STATUS](AI2-STATUS.md), [BACKLOG](BACKLOG.md), and [the team roster](production/team.md) at that revision before editing.
- Follow [the studio workflow](production/workflow.md). Producer selects and hands off the work, relevant specialists implement it, lead-programmer reviews the final diff, and qa-lead verifies the acceptance evidence. These responsibilities apply in a single conversation as well as in a multi-agent session.
- ORK 3 owns combatants, combat, inventory, equipment, quests and saves. Makinom owns interactions and story schematics. Unity owns 2D rendering, physics, input and animation. Keep each gameplay state in one place. G1 uses UGUI and SpriteRenderer / Tilemap.
- Keep original asset GUIDs and commit each game-owned asset with its `.meta`. Keep licensed dependencies in an authorized checkout or runner unless the applicable license and repository access allow storing them in Git.
- Use fast-forward updates. Keep the repository public as most recently authorized by the user; do not change visibility without a newer explicit instruction. Public availability does not grant redistribution rights to third-party licensed assets. The user manages development scheduling. The user runs ongoing development from standard ChatGPT chat with the GitHub plugin. Follow [the ChatGPT entry point](CHATGPT.md).

- **Framework changes are authorized after sufficient validation.** ORK/Makinom framework code, DLLs, settings, configuration and game data are not read-only. Make necessary changes in isolated candidates, record baseline/impact/rollback, preserve provenance and references, and pass the affected paths at the final SHA before integration. Follow [framework validation](production/workflow.md#框架修改与验证); do not ask for routine approval. Keep a single RPG authority, UGUI, existing licensing, and zero new spending. Version changes need the same evidence, not a blanket ban or an automatic upgrade.
- **Autonomous delivery and verification:** do not require the user to playtest, review media, run tools or post GitHub feedback. Agents run available checks and record defects, unknowns and blocked evidence in [known issues](production/KNOWN_ISSUES.md). No human-feedback gate; no claim that automation proves enjoyment. Record both implementation and agent-verification next steps.
- Prioritize merging a ready, verified candidate before unrelated governance changes; allow independent work and urgent changes. Reuse trustworthy evidence only for identical final SHA and equivalent verification conditions. Do not impose a fixed WIP cap or a broad test-refactoring milestone.
- Prefer released, Unity-version-compatible official Unity Registry packages or built-in features, but **plan first; install only in isolated, same-SHA-validated candidates**. Evaluate URP 2D, Input System in **Both** mode, Cinemachine 3, 2D animation, Tilemap Extras, audio mixer, Sprite Atlas V2, conditional Pixel Perfect, localization, profiling and Build Profiles; defer Addressables/ECS/HDRP until their need is demonstrated. No paid services or extra CI spending without new authorization.
- **Current user decision (2026-11-10): no automatic M1–M11-before-Story-003 priority.** Modernization M1–M11, game stories, gameplay, narrative, and regression fixes are all eligible workstreams. Pick the next independently verifiable increment by real player value, live dependencies, unresolved defects, and the current handoff—not by a mandatory migration sequence or an automatic story preference. CI that is queued/running does not force idle time or forbid independent work on another candidate; keep the tested SHA untouched, review the CI when it finishes, and fix actual failures before accepting/merging the affected increment. No unrelated work may be merged on an unverified dependency. Conditional M stages may be skipped with evidence; do not install packages just to check a box. Each `codex/pending/*` candidate is one verifiable increment, and on actual merge into `codex/dev`, close it and safely clean only this candidate and directly superseded candidates; follow [branch lifecycle policy](production/workflow.md#候选分支清理). Never extend a merged branch; continue the same feature from the latest dev on a newly named candidate. [Automatic cleanup](.github/workflows/close-merged-pending.yml) requires exact-SHA Unity verify evidence; check the run and remote result, and note GITHUB_TOKEN push does not recursively trigger workflows. The [migration stage index](docs/technical/MIGRATION_STAGE_BRANCHES.md) remains historical/technical reference, not a global priority queue. Preserve UGUI, same-SHA CI, ORK/Makinom ownership, and gameplay-story continuity; a documentation-only update is not installation or acceptance evidence.
