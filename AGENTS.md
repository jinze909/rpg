# RPG development

- Product priority: **fun comes first**. Every story, content, system and production decision must serve an engaging player experience. Scope, word count, feature count and technical completion do not establish that an experience is fun. State what players actually do, discover or care about; validate uncertain assumptions through play and revise or remove elements that weaken the experience. Narrative depth and content scale remain goals on this foundation.
- The current narrative baseline is the [Return story outline](docs/narrative/STORY_OUTLINE.md) and its current companion drafts under `docs/narrative/`; [handoff](docs/narrative/HANDOFF_FOR_CODEX.md) records the original reading order, not a separate competing canon. Reconcile old candidate merges against the latest `codex/dev` narrative and never restore superseded drafts. Narrative P0, technical P0 and existing Unity S00 are distinct. This is a writing/design baseline, not implemented gameplay or proof of fun. Preserve the midpoint reunion, substantial shared adventures afterward, and independently worthwhile regional stories.
- Read the [one-page gameplay baseline](docs/gameplay/BASELINE.md) before gameplay work. Preserve its distinction between decided direction, provisional prototype controls and unvalidated hypotheses; task execution must not silently promote the latter two into product requirements.
- Work in `jinze909/rpg`. Resolve the live `codex/dev` HEAD and read [AI2-STATUS](AI2-STATUS.md), [BACKLOG](BACKLOG.md), and [the team roster](production/team.md) at that revision before editing.
- Follow [the studio workflow](production/workflow.md). Producer selects and hands off the work, relevant specialists implement it, lead-programmer reviews the final diff, and qa-lead verifies the acceptance evidence. These responsibilities apply in a single conversation as well as in a multi-agent session.
- ORK 3 owns combatants, combat, inventory, equipment, quests and saves. Makinom owns interactions and story schematics. Unity owns 2D rendering, physics, input and animation. Keep each gameplay state in one place. G1 uses UGUI and SpriteRenderer / Tilemap.
- Keep original asset GUIDs and commit each game-owned asset with its `.meta`. Keep licensed dependencies in an authorized checkout or runner unless the applicable license and repository access allow storing them in Git.
- Use fast-forward updates. Keep the repository public as most recently authorized by the user; do not change visibility without a newer explicit instruction. Public availability does not grant redistribution rights to third-party licensed assets. The user manages development scheduling. The user runs ongoing development from standard ChatGPT chat with the GitHub plugin. Follow [the ChatGPT entry point](CHATGPT.md).

## 视觉与 UI 验收红线（强制，2026-11-19）

- **正常 RPG 地图尺度**：严禁把主要可玩关卡/地图压缩在过小的盒状区域内，所有主要可探索场景须达到正常 RPG 地图尺度（支持镜头跟随与清晰空间分区）。
- **严禁遮挡可玩区域**：严禁任何 UI 按钮、面板遮挡可玩地图、墙体或角色。
- **严禁双层标题重影**：严禁两层 Canvas 同时显示标题导致文字重影；进入战斗或子界面时必须隐藏底层冲突标题、对话与入口按钮。
- **严禁调试文本墙**：严禁把 `BuildBattleReadout` 这类多行纯文本调试快照直接糊在屏幕中央；战斗信息必须以安全留白区的紧凑状态卡、可视化血条与指令栏呈现。
- **严禁粗圆海报字作正文**：严禁正文与按钮使用粗圆海报艺术字（如 `ZCOOLQingKeHuangYou`），必须使用清晰锐利的开源像素字体（如 Fusion Pixel 12px/10px）。
- **安全留白与统一视觉规范**：所有新增/修改的 UI 必须在安全留白区排版，并带统一深色底板与细边框；每次视觉/UI 升级必须输出并自查实际 GameView 截图，确认无文字重影、无按钮压地图、无字体粘连。

- **Framework changes are authorized after sufficient validation.** ORK/Makinom framework code, DLLs, settings, configuration and game data are not read-only. Make necessary changes in isolated candidates, record baseline/impact/rollback, preserve provenance and references, and pass the affected paths at the final SHA before integration. Follow [framework validation](production/workflow.md#框架修改与验证); do not ask for routine approval. Keep a single RPG authority, UGUI, existing licensing, and zero new spending. Version changes need the same evidence, not a blanket ban or an automatic upgrade.
- **Autonomous delivery and verification:** do not require the user to playtest, review media, run tools or post GitHub feedback. Agents run available checks and record defects, unknowns and blocked evidence in [known issues](production/KNOWN_ISSUES.md). No human-feedback gate; no claim that automation proves enjoyment. Record both implementation and agent-verification next steps.
- Prioritize merging a ready, verified candidate before unrelated governance changes; allow independent work and urgent changes. Reuse trustworthy evidence only for identical final SHA and equivalent verification conditions. Do not impose a fixed WIP cap or a broad test-refactoring milestone.
- Prefer released, Unity-version-compatible official Unity Registry packages or built-in features, but **plan first; install only in isolated, same-SHA-validated candidates**. Evaluate URP 2D, Input System in **Both** mode, Cinemachine 3, 2D animation, Tilemap Extras, audio mixer, Sprite Atlas V2, conditional Pixel Perfect, localization, profiling and Build Profiles; defer Addressables/ECS/HDRP until their need is demonstrated. No paid services or extra CI spending without new authorization.
- **Non-blocking CI handoff (2026-11-11, mandatory):** A pending/queued/running Unity CI blocks validation/merging of that exact candidate SHA only, **not new independent implementation**. During every dispatched development turn, maintain (A) existing candidate/CI triage (latest SHA; stale failing SHA superseded by a newer queued fix is not an actionable fresh failure) and (B) independent, non-overlapping gameplay/code/test/resource development on another candidate from current dev. If all available candidate CI is queued, proactively select unclaimed valuable work from BACKLOG/stories, make a real change, and commit it to a separate candidate without modifying tested refs. Never end with only 'CI still running' unless every feasible independent task has a specific demonstrated dependency/conflict/permission blocker. Do not fabricate commits, rerun duplicate CI, edit schedules, or create busywork. Details in [workflow](production/workflow.md#ci-排队运行时必须继续独立开发). Already queued runs require no polling loop. Never overwrite newer guidance when rebasing an old pending branch.
- **Current user decision (2026-11-10): no automatic M1-M11-before-Story-003 priority.** Modernization M1-M11, game stories, gameplay, narrative, and regression fixes are all eligible workstreams. Pick the next independently verifiable increment by real player value, live dependencies, unresolved defects, and the current handoff—not by a mandatory migration sequence or an automatic story preference. CI that is queued/running does not force idle time or forbid independent work on another candidate; keep the tested SHA untouched, review the CI when it finishes, and fix actual failures before accepting/merging the affected increment. No unrelated work may be merged on an unverified dependency. Conditional M stages may be skipped with evidence; do not install packages just to check a box. Each `codex/pending/*` candidate is one verifiable increment. On actual merge into `codex/dev`, close it; automatic cleanup retires only completed, CI-inactive heads whose whole changes are proven by exact-SHA Unity verification, a verified descendant, or a verified exact changed-file snapshot in dev history. Other diverged work remains untouched. Follow [branch lifecycle policy](production/workflow.md#候选分支清理). Never extend a merged branch; continue the same feature from the latest dev on a newly named candidate. [Automatic cleanup](.github/workflows/close-merged-pending.yml) requires exact-SHA Unity verify evidence for the proof commit (not necessarily the obsolete original SHA); check the run and remote result, and note GITHUB_TOKEN push does not recursively trigger workflows. The [migration stage index](docs/technical/MIGRATION_STAGE_BRANCHES.md) remains historical/technical reference, not a global priority queue. Preserve UGUI, same-SHA CI, ORK/Makinom ownership, and gameplay-story continuity; a documentation-only update is not installation or acceptance evidence.
